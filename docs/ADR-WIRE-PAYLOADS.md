# TCP/WebSocket payload fidelity and bounded transport

The TCP sender previously accepted only strings and exposed received bytes only after UTF-8 conversion. Interactive TCP decoded each chunk independently, corrupting a multi-byte character split across packets. WebSocket used a client without this application's explicit native frame-size cap and handled Blob conversion asynchronously, which could append a late event after completion.

Both send paths now use a shared bounded payload codec: legacy strings, explicit utf8/base64/hex objects, and explicit fixed-width or delimited text packets. Every wire payload is at most 1 MiB; binary encodings are canonical/validated before allocation. Fixed widths count UTF-8 bytes, use single-byte padding, and reject overflow rather than silently truncate. Delimited packets retain empty positions and have an explicit trailing-delimiter option; they are not CSV escaping or claimed native Apipost format equivalence. Saved protocol definitions can retain the payload and TCP receive encoding, and reload validation preserves those fields.

One-shot TCP responses retain their existing text body plus exact base64 and byte size. Text is only a convenience view for arbitrary binary data. A duration-cut response explicitly reports timedOut/partial, not a confirmed complete application message. Interactive TCP supports utf8/hex/base64 receive views; the UTF-8 decoder spans chunks. TCP chunk events are not application message boundaries.

WebSocket reuses ws 8.21.3 (MIT) directly, including its maintained framing, masking, UTF-8 validation and control-frame handling. Native maxPayload is 1 MiB; accumulated retained message data still uses the existing 1 MiB ceiling for one-shot exchanges. Compression, redirects and automatic reconnect/replay are disabled. Client authentication headers are explicit and bounded; protocol-owned headers cannot be overridden. WSS always verifies the certificate, supports explicit CA and paired client certificate/key, and never permits a rejectUnauthorized override. Credentials remain per connection, not in saved definitions or snapshots. Inline URL credentials are rejected.

Received WebSocket events state utf8/base64 encoding, including empty binary messages. Interactive sends report queued/written/failed as local transport progress, never remote application acceptance. Closing/aborting suppresses late message mutations. Existing live-session, retained-event, preview and aggregate limits remain; previews are not full large-message evidence. Existing global interactive sessions are still local-authenticated diagnostic sessions, not a new claim of project-scoped persistent execution history.

Tests cover real TCP binary exchange, UTF-8 packet splits, saved definition reload and reuse, real WebSocket text/binary/empty frames, subprotocol/header authentication, oversized native frames, pre-abort without connection, strict TLS/mTLS, and interactive stop. The existing browser/three-platform CI remains required.

REA's selected original TCP module statically identified fixed/delimited/ISO8583 modes. The original sample was not executed, and its internal implementation is not copied. The candidate iso_8583 2.6.7 ISC dependency was evaluated outside the product tree: npm audit reports a critical xmldom dependency path through jxon, so it was **not** added to production or called complete. ISO8583, original format migration, TCP response framing, TCP TLS and full original script semantics remain separate gaps.

A subsequent explicit-profile ISO8583 adapter is described in [ADR-ISO8583-CODEC.md](ADR-ISO8583-CODEC.md). It uses a different dependency without the rejected XML chain; original native-profile migration is still not claimed.
