# OAuth1 OOB/PIN token acquisition

Explicit manual UI action can request an OAuth1.0a temporary credential, show the provider authorization URL, then exchange the user's verifier/PIN for an access token and secret. This is an OOB-supporting provider flow, not automatic sign-in, a callback-server flow, or arbitrary third-party account management. Unsupported providers must still supply existing credentials. Endpoints must use HTTPS except loopback HTTP; fragments, embedded URL credentials and prepopulated OAuth protocol query keys are rejected. Explicit consumer configuration is used, not environment/OS credentials or unresolved variable templates.

Request/access-token POSTs use the existing reviewed OAuth1 HMAC/RSA signing implementation. HTTP redirects are not followed. Token responses are bounded and reject duplicate/missing fields; temporary responses must confirm oauth_callback_confirmed=true. Temporary secrets stay only in server memory, never in the returned authorization link. Flow IDs are random, expire after5minutes, and at most10 concurrent flows reserve their slots before network I/O. Completion consumes a flow even on failed exchange, rejecting concurrent reuse. App close aborts pending exchanges and clears the map. Expired entries are pruned on access.

The UI confirms initiation, requires manual provider authorization and verifier entry, refuses to overwrite changed/project-switched credentials, and leaves obtained tokens in unsaved editing state. Existing app save/export plaintext warnings remain. All endpoints require the authenticated local session and origin restrictions; MCP is not granted new OAuth tools. Desktop browser-opening allowlist admits only the exact pending authorization URL.

Tests cover actual loopback request/access exchange, independent HMAC verification for both temporary and token-secret stages, no secret in URLs/results, invalid endpoints/responses, expiration/replay/concurrency and API authorization. Browser exercises cancellation, explicit start, link/verifier, token application and subsequent signed requests against a fake local provider. No real provider/account was used.
