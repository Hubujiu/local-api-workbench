# 沙箱内有界 JSON5

原版 apipost-runtime8@3.1.9 静态代码使用 JSON5（来源见 ADR-SCRIPT-DIALECT）。本工具独立接入官方 json5@2.2.3（MIT，https://github.com/json5/json5），固定版本、打包第三方许可；不运行原版代码。

提供全局 JSON5 与准确模块名 require('json5')。parse 支持注释、单引号、非引号键、尾逗号、十六进制等 JSON5 数据语法，支持 reviver；stringify 支持 replacer 与缩进。解析、回调和序列化全部在现有 QuickJS 内进行，无 Node、文件访问或新网络权限。

边界：parse 输入必须为字符串且不超过64KiB UTF-8；stringify 输出不超过64KiB。序列化前检查普通数据属性：单个字符串/属性名64KiB，10000访问节点、32层；不为预检重复求值 getter。该限制是本工具显式子集，包括即使 replacer 后可能缩小的数据也提前拒绝超限。循环引用保留库的失败语义；用户 getter/toJSON/reviver/replacer 和复杂输入仍可能先触发原有250ms计算、2秒总截止、16MiB内存限制。返回到项目时仍遵循既有JSON持久化规则，非有限数不保证无损保存。

曾发现大字符串先进入 JSON5 逐字符序列化，会先超时而非触发明确字节错误；新增数据预检后保持原字节拒绝断言通过，没有扩大预算或放宽断言。回归覆盖中文字节超限、注释/尾逗号/十六进制往返、reviver/replacer、深度及 __proto__ 为自身数据属性但不污染对象原型。真实浏览器和三平台包内调用纳入现有 CI，是否完成以对应提交结果为准。

这不等于完整 Apipost SDK/Mock.js/jsonpath 支持。

本地全量验收曾出现9项既有脚本用例 total-deadline 超时（370项中361通过）；保留原日志并按同一预算/并发重跑，不将后续通过等同于根因已确认。没有扩大2秒总截止或修改原语义断言。

进一步诊断：超时记录增加可信 worker 最后阶段与实际耗时，定位到 bootstrap（尚未运行用户脚本）。JSON5 改为独立、可复现的静态 bundle，仅首次在 VM 中访问 JSON5 时初始化，避免所有既有脚本无条件加载解析器；不是在主机解析数据。初始化仍计入现有运行预算，未延长任何超时。无 JSON5 的公共 bundle 恢复为493958字节。针对 Ajax/兼容层/迭代数据/JSON5 的21项回归全部通过，完整与跨平台验证须查看对应检查点；不凭一次通过断言所有时间抖动根因已排除。

惰性加载后仍曾见不同既有用例超时：370项中368通过，涉及XML初始化；直接传入VM字符串、避免每次解析包源码字符串后，另一轮仍有生命周期与共享阶段两项失败（生命周期主定时器实际3474ms才触发）。这些现象尚不能归因于单一新库；正在以已通过CI的e2b8135运行器文件/公共库进行隔离对比，原工作区不回退、不更改预算，保留所有失败记录。

对照结果：隔离副本恢复远程 e2b8135 的 scripts.mjs / script-worker.mjs / 公共库，Git blob SHA 均逐一核对一致，排除新增JSON5测试，367项中366通过，原共享脚本回调顺序测试同样因 total-deadline 失败。说明当前环境存在旧运行器也能触发的时限问题，不能只归因于JSON5，也不能声称已经找到唯一根因。正式时限和断言继续保持。

后续尝试将所有库拆为按需模块，但发现把既有工具/XML初始化移入用户阶段会改变原预算归属。因此撤回该实验，保留所有既有库的原bootstrap初始化；只对新增JSON5按需加载。原公共库Git blob仍为024b863228422ef644618f2162305e22cd558b1c，与e2b8135一致。没有为了新功能降低既有脚本的有效运行预算。

最终本地JSON5/旧XML集中15项通过，旧运行器对照仍有时间波动；全量验收曾有非JSON5既有用例超时，须通过同一PR的独立跨平台CI继续核验，未声称本地全量全绿或唯一根因已解决。
