# Native TCP/WebSocket/SSE steps in fixed execution plans

A step with type `protocol` freezes a project-local protocol definition (or an explicit definition), message template, duration/capture limits, expected native status, extraction paths and assertions. Saving resolves definitionId within that project. Later edits to the saved protocol definition cannot redirect or change the frozen plan. Endpoints are not runtime-interpolated; only the message template is interpolated. Static payloads are validated at save time and resolved templates are validated before their own network operation.

Native outcomes remain completed/partial/failed/cancelled in protocolResult; no synthetic HTTP 200 response is invented. Default expectedStatus is completed. Accepting a bounded stream/capture requires explicitly expecting partial. Assertions and extraction use the native result JSON and real duration. Successful extraction can feed runtime/environment/global scopes and later real HTTP steps, with the existing scope commit rules. Protocol scripts and original native plan migration are not implemented by this adapter.

Execution is available through the authenticated project HTTP run API, execution-authorized MCP run_plan, and the existing CLI. The CLI currently supports unauthenticated native steps, not a new credential flag. Missing executor authorization fails rather than making a hidden request. MCP read-only access does not grant execution.

Per-run protocolCredentials maps exact unique step IDs to temporary headers/TLS/subprotocol options. It cannot change a target or definition. The complete map is preflight-validated before any plan step runs, including earlier HTTP steps. WebSocket uses the existing strict TLS/header configuration validator; SSE accepts bounded non-transport header values; TCP does not silently accept unsupported TLS/HTTP credential settings. Credentials are not inserted into plan snapshots, variables or persisted evidence. A later run without them is not implicitly authenticated. Response data can still contain sensitive application values and is not automatically scrubbed.

The HTTP server shares a five-call native-protocol slot pool between one-shot calls and plan/MCP steps. Existing gRPC/Socket.IO limits remain separate. Cancellation propagates to the real transport and prevents subsequent steps. The completed plan uses the existing durable run writer; persistence failure must not replay network steps.

Tests cover TCP -> runtime extraction -> actual HTTP, real SSE/WebSocket header authentication, explicit partial outcomes, concurrent credential isolation, invalid credentials before any earlier side effect, cancellation, timeout failure, static payload refusal, saved-definition freeze, HTTP/MCP/CLI execution with persisted evidence, read-only denial, shared call-limit refusal and slot reuse after cancellation. No new frontend controls or claim of full original protocol scripting compatibility are included.
