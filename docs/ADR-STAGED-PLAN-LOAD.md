# Bounded staged load of saved HTTP plans

This is a backend-only, constrained staged-load contract. It reuses `runPlan`, the existing request transport, script sandbox, frozen plan and per-iteration variable/cookie isolation. It does not attempt to run the original application's worker, copy its code, or claim its native event format is completely understood. The original static implementation's intermediate ramp-up starts omit the initial hold offset; this contract instead makes all stage offsets cumulative.

`POST /api/projects/:id/staged-load` accepts `planId`, optional `environmentId` and `runId`, and `schedule` with `initialVUs`, `stages: [{durationSeconds, targetVUs}]`, `maxIterations`, and optional `reportIntervalSeconds` (1–10, default 1). The plan must be a saved HTTP plan with 1–10 worst-case expanded active request steps, no collection scope or redirect, and no native writes. Canonical condition and repeat groups, including runtime rows, use the existing plan executor; disabled steps do not execute but still undergo model validation. Runtime-row groups reserve their `maxRows` worst-case HTTP count, never the eventual source length, within the same request and aggregate limits. Both preparation and direct execution validate the static graph without reading row sources or running scripts/transports. Live references are frozen before admission and remain fixed for the entire staged invocation. Non-HTTP protocol steps remain unsupported. The snapshot is at most 1 MiB. Initial/target VUs range from 0–10, each of 1–10 stage durations is a positive whole second, total duration is at most 60 seconds, and `worst-case expanded steps × maxIterations` is at most 100. A ramp changes VUs in integer increments at equally spaced offsets; downscaling lets an already-started iteration finish and does not admit another for that slot. A delayed event loop reconciles directly to the target at the current monotonic time instead of replaying expired increases. The total deadline interrupts remaining work. Iteration limit stops admission but does not remove the total deadline. A ramp from zero reaching its first VU exactly at the final deadline may perform no iterations.

Periodic reports continue even while requests are in flight. An SSE response emits `start`, zero or more `report`, `reportEnd`, and `complete`. The internal report observer is synchronous; if it throws or returns a promise, admission stops and in-flight work is cancelled. Reports contain only counters, step IDs, response-byte totals, and duration percentiles; only plans with active runtime-row definitions add `iterationOutcomes`, containing the fixed counters `passed`, `failed`, `cancelled`, `runtimeRowsInvalid`, and `executionError`; they do not include URLs, bodies, headers, variables or remote errors. Per-step timings are HTTP response-duration samples in milliseconds, and P50/P90/P95/P99 use the nearest-rank method; `timingSamples` discloses how many responses had a duration. Rate fields are cumulative completed steps or iterations divided by elapsed time, not the original product's QPS or interval throughput. Values are bounded by the admission limits, so exact sorting is used instead of a histogram. Stop reasons distinguish `iteration-limit`, `duration`, `cancelled`, and `observer-failed`. A runtime-row source failure retains already-completed producer statistics, does not replay the producer, and does not expose the source value or original error. Runtime frames, scopes and cookies are isolated per iteration. The report is transient and is not saved as project history.

Explicit `/api/cancel` keeps a connected SSE caller and emits a cancelled terminal report; a disconnected caller aborts in-flight work and emits nothing further. Cancellation cannot undo a request already delivered to a remote system. Native database access is not enabled for this execution entrypoint. Active runtime-row plans reject potential declarative database operations during static admission, including operations under false conditions. Plans without active runtime-row groups retain their existing runner failure behavior without being granted new capabilities. This endpoint can send real requests only when the authenticated owner invokes it. Tests use loopback peers only.
