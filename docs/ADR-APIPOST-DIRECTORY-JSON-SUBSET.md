# Experimental original-directory JSON subset

The import dialog can explicitly select an original project directory containing project.json. The browser reads only selected, whitelisted UTF-8 JSON files and sends a bounded file manifest to the existing local atomic import endpoint. No server filesystem path, original executable, compiled fileDB module, plugin, linked attachment, or imported script is executed. The source files are never written.

The independent assembler follows static read/write observations in the official offline 2.0.0 package: collection indexes contain project_id/items; APIs and samples persist detail objects under data; schemas combine data with outer model identity; environments contain server_list/env_var_list; settings resources have separate JSON files. It reconstructs a modern interchange document and reuses the existing limited converter, including all unsupported-resource refusals and inheritance protections.

Supported paths are project.json, global_params.json, global_vars.json, apis/envs/samples/schemas indexes and records, and explicitly mapped settings custom_funcs/db_links/marks/custom_attrs/code_list/mock_custom_rules/desc_list. A recognized settings filename does not imply its nonempty content is supported by the modern converter. In particular custom functions, database dependencies and custom Mock rules still fail explicitly. Unrecognized files, including installation preferences, internal Mock defaults, reports, histories, extra attachments, Git metadata and backups, are not silently ignored: the selected directory is rejected. This deliberately narrow subset is not yet a general native project migration.

Limits are 5000 files and 4 MiB aggregate input, checked before browser reads. Paths must be relative whitelisted names; traversal, duplicate paths, mixed selected roots, invalid UTF-8, changed-size reads, wrong project IDs, missing records/indexes, orphan records and contradictory identity/metadata fail. Assembly and the subsequent import are atomic. Closing the dialog while reading files or changing its target prevents a later unintended import. Existing single-file imports also receive this target guard.

Validation uses independently authored synthetic directory fixtures based on the inspected structure, not vendor-generated directories. Tests cover structural assembly, rejection boundaries, retained environments/model/sample links, real HTTP environment resolution, unchanged inputs, unsupported dependency rollback, and actual browser directory selection. These checks prove the implemented subset, not real-world original fileDB flush/recovery compatibility. A genuine original-created directory and broader resource round-trip are still needed before calling native migration verified or complete.
