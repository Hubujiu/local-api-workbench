# SQLite native execution termination

The previous worker deadline could reject a query while a long native SQLite call continued running. `Worker.terminate()` did not interrupt that native call promptly. A real recursive-query reproduction kept its Node caller alive beyond an outer seven-second boundary after reporting a two-second timeout.

Bounded reads and opt-in writes now execute once in an owned, non-shell child process. The existing two-second deadline and execution worker’s 64 MiB JavaScript old-generation limit are unchanged. A separate 16 MiB supervisor heap keeps lifecycle handling responsive while SQLite executes in that worker. The limit is not a total native-memory/RSS guarantee. The child never evaluates SQL as JavaScript, loads SQLite extensions, or starts descendant processes. Its supervisor kills the entire owned process on its own deadline or parent-channel disconnection, so a lost parent cannot abandon a native query. At the deadline the parent requests hard termination and only settles after the child's close event. Receiving an IPC message or successfully sending a kill signal alone is not termination evidence.

The child receives no inherited execArgv or NODE_OPTIONS, so caller `--input-type`, debug/test flags and heap overrides cannot invalidate its launch contract. Electron launches its own executable in Node mode, only for this owned child; renderer isolation, sandbox and TLS settings are unchanged. Packaged desktop read/write smoke tests remain required on all three platforms.

An interrupted write is **outcome unknown**, not “rolled back” and not retryable by default. The operation might have committed before termination or lost its reply. No automatic mutation replay occurs. SQLite may leave a hot journal; normal authorized read-write access can perform SQLite's own recovery. This implementation does not delete journals, open a user database for an extra recovery write, or claim that a read-only connection can always recover a hot journal. The caller must inspect/recover the database before deciding whether another write is safe.

Tests cover real recursive-query termination, a write trigger that creates a journal and then stays in native computation, natural caller-process exit, native journal recovery, absence of committed trigger effects in that fixture, release of the write lock, subsequent independent reads/writes, ordinary SQL errors and unsendable IPC input. The write fixture establishes rollback for that pre-commit case, not for every possible interruption point. Existing explicit-write, single-DML, parameter, result-size, change-count and transaction checks remain in place.

Reference: [Node child-process lifecycle and kill semantics](https://nodejs.org/api/child_process.html#subprocesskillsignal).
