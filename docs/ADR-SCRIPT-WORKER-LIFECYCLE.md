# 脚本工作线程正常退出与生命周期

## 可复现的问题

原实现收到脚本结果便立即 resolve/reject，同时不等待 worker.terminate()。Worker 又在 postMessage 之后才 dispose QuickJS。结果是下一轮压测已开始，而上一轮线程还在清理或被强制终止。独立子进程固定回归在旧版本成功返回后立即检测到 3 个仍活跃的 MessagePort，证明“已完成”早于资源释放。

修复顺序：先在 worker 内完成 QuickJS 句柄、context/runtime 清理，再发送结果并关闭消息端口；父线程等正常 exit 后才返回结果。正常成功/脚本错误不再主动 terminate。取消、总超时、越权网络等仍立即中断，等待 terminate 完成后再拒绝。2秒总截止包含清理时间，250ms活动预算、内存及网络限制不放宽。

固定子进程验收：5轮，每轮4个并发成功、4个脚本错误、4个取消；每一批完成后端口数必须回到基线，不允许用延时等资源自然消失。原脚本/HTTP/取消/定时器/Promise回归全部继续运行。

## 尚不能作出的结论

c32b768 的 Windows核心测试两次发生进程级失败：首次 load-data.test.mjs 的 TAP 记录退出码3221225477（0xC0000005），第二次发生在 builtin-variables.test.mjs；浏览器、其他核心和三平台实际桌面成功。第一次诊断产物12237865420，第二次12237208466，均来自Actions39360846438。旧代码确实存在生命周期竞争，但没有原生崩溃调用栈，不能仅凭退出码就断定它是这些Windows崩溃的唯一根因，也不能用单次重试绿替代证据。后续精确提交CI继续验证。

Node工作线程退出行为依据：https://nodejs.org/api/worker_threads.html 。不禁用WASM保护、不放宽安全沙箱、不跳过Windows测试。

本地默认8个测试文件并行时，新生命周期压力fixture与其他VM测试叠加，使简单CSV脚本有一次在651ms总耗时内触发250ms活动时限；原断言保持失败。测试文件并发现固定为2（本地/CI一致），各测试内的多线程/并发请求、全部用例及生产预算完全保留。目的是避免测试文件级CPU超配；没有延长脚本时限、跳过压力覆盖或自动重试失败。该调度修改也不能证明Windows原生崩溃原因。

77189b2 首轮9/10通过，Windows不再出现此前进程级错误，但原HTTP并发限制断言暴露另一个确定性问题：根脚本已被拒绝，完成循环仍等待4个挂起HTTP超时，再输出根错误；在慢环境中先撞到2秒总截止，掩盖“同时4次”错误。新增先失败的固定回归验证根错误必须直接中断子请求（证据状态interrupted，而非等待超时failed）。每次排空微任务后检查根Promise拒绝并立即结束，错误文本通过原生安全追踪器读取，不执行用户getter；所有原始截止保持。
