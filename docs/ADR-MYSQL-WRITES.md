# Explicit bounded MySQL writes

The manual database HTTP endpoint accepts MySQL INSERT/UPDATE/DELETE only with allowWrite:true on that call and explicit host, database and user. Default queries, registered database sessions and script operations remain read-only. This is a backend addition; no new frontend controls are added.

Reuse mysql2 and the Apache-2.0 node-sql-parser 5.4.0 MySQL grammar. Parsing runs in a separate 128 MiB worker with a two-second deadline; it executes no SQL and exits before any database connection. Reject batches, non-DML, aliases/joined targets, external schemas, CTE/subqueries, INSERT SELECT/IGNORE/duplicate-key forms, comments and backslash syntax. Use bound parameters for data containing those characters. SQL is sent as the original single statement, not rewritten by a home-grown SQL generator. Input is capped at 50000 characters and the existing parameter limits; AST traversal has node/depth limits.

Each operation owns its data connection and a second cancellation connection with the same explicit target and credentials. Both may use the existing pinned SSH channel helper; there is no direct fallback. At most five writes are active. Connections are transient and destroyed at completion. The transaction first obtains a metadata lock with a zero-row target SELECT ... FOR UPDATE, then verifies an InnoDB base table through parameterized metadata lookup. This prevents a concurrent engine change between validation and mutation. Accounts without SELECT/metadata access and the privileges required for FOR UPDATE (UPDATE, DELETE or LOCK TABLES in addition to SELECT) fail before the DML; no grants are created.

Execute one prepared DML statement with multipleStatements:false and FOUND_ROWS enabled. UPDATE counts matched target rows, including unchanged values. Reject more than 1000 target rows, malformed row counts or server warnings and request rollback. INSERT VALUES has a preflight 1000-row limit. A confirmed COMMIT is required before returning committed:true. Commit-acknowledgement or rollback uncertainty is reported explicitly without retry. The cap does not count every cascade/trigger effect; auto-increment allocation, nontransactional trigger effects and external effects are not promised to roll back.

Every invocation owns the public custom stream for both data and cancellation connections before authentication (or the existing pinned SSH transport). Each connection, including SSH setup, has a three-second limit. Every transaction setup, target metadata-lock query, prepared metadata lookup, prepared DML, COMMIT and ROLLBACK phase has a two-second limit. The prepared-statement phase includes PREPARE **and** EXECUTE, not merely mysql2's execution callback timeout. A stricter eight-second whole-operation budget starts before parsing and covers both connections and all phases; the existing parser's two-second worker limit is unchanged. These limits cannot be increased by HTTP input.

At a DML deadline, first request KILL QUERY for only the known ID of this operation's own data connection and immediately force-close the data transport. KILL is best effort, bounded by one second and the remaining whole-operation budget; the control transport is then force-closed too. At every awaited boundary, stopped state is checked before any later SQL can be queued. Never use mysql2's graceful destroy/end as the close boundary, nor Promise.race alone as cancellation. Both actual local transport close events are awaited before releasing write capacity; SSH capacity remains owned until its underlying local transport closes. The eight-second budget limits active work, not event-loop scheduling latency or a promise of instantaneous remote cleanup.

Before DML is attempted, a timeout reports that no user DML or COMMIT was sent. After a DML attempt, a timeout reports that no COMMIT was sent and rollback has not been confirmed. KILL is reported as attempted only if requested. Closing the local socket, a KILL acknowledgement, or a disconnected HTTP client is not proof of remote termination or rollback. Only a genuine ROLLBACK acknowledgement permits the existing confirmed-rollback wording. After COMMIT has been attempted, lack of an acknowledgement is an unknown commit outcome: never report success, claim rollback, issue a speculative rollback, or retry. An observed COMMIT acknowledgement remains a success during teardown. Driver error strings are not reflected because they can contain SQL/bound values or credentials; responses retain the phase and outcome category. No privilege grant, system setting change or automatic replay is performed.

The owner HTTP request's disconnection deliberately does **not** cancel an explicitly authorized write. It keeps the existing per-call write intent and bounded acknowledged/uncertain outcome contract, independently of read-only request cancellation. No script, session, CLI or MCP path receives write authority.

The existing disposable MySQL CI service runs real HTTP opt-in, exact bigint/blob write/readback, update/delete, duplicate-key rollback, unchanged UPDATE row counting, over-limit rollback, warning rollback on a non-strict fixture session, read-only grant rejection, timeout/readback, a concurrent own-DDL metadata-lock check and pinned SSH writes. Independent raw-wire loopback tests exercise the actual mysql2 client through successful metadata/DML/COMMIT and held/error phases, including half-open peers, owner HTTP, isolation, capacity and restart. These peers model protocol/lifecycle faults, not a transactional database engine. Local driver-contract tests separately cover late completion, acknowledged commit during teardown, commit/rollback uncertainty and cancellation targeting. Running those contract tests alone does not count as real database validation.
