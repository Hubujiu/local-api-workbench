# Bounded original numeric Mock rule import

Static inspection of the official offline 2.0.0 UI/export and generator bundles identifies custom rule identity, field type, exact/wildcard matching, case flag, generator type, expression and description. The schema generator selects the first rule with the same field type; exact matching compares field names after optional lowercasing. Numeric fields with minimum or maximum bypass these rules. A separate metadata sampler is not treated as the data-generation contract.

Modern JSON and supported native-directory JSON imports accept at most 100 explicit numeric rules: integer/number, exact ASCII identifier-like field names or bounded star/question/ASCII-class/brace-alternative wildcard patterns up to 100 characters, match_case 1 or -1, mock_type 1, and @integer(min,max) or @natural(min,max) with two decimal safe integers in the existing ±1e12 bounds. Natural bounds cannot be negative. Unsupported rule fields, Unicode/POSIX-class/nested-brace/brace-range/globstar patterns, system expressions, other types/functions, unknown flags and conflicting source identities fail the entire import. No expression or source script executes during import.

Rules keep source identity through normalization, storage and editor changes. Imported number rules do not also match integer fields. Schema examples/defaults/enums retain existing priority. Matching imported rules with exclusive bounds or multipleOf (without minimum/maximum bypass) fail explicitly instead of silently adjusting the source numerical range. Other unsupported schema combinations retain existing safe sample validation. This does not implement all original generators, random distributions, full wildcard semantics, builtin-rule settings or all schema constraints. Existing target rules stay first; imports do not replace existing settings or enable builtins. Re-import of unchanged rules is idempotent; edited source identities conflict rather than being silently overwritten.

The rule editor exposes the restricted imported mode. It retains source metadata and rejects edits outside this subset; users can create an independent native rule for other Local API behavior. No broader network, script, file or credential permission is granted.

Tests use independent synthetic JSON/directory fixtures, constant-range numerical oracles, exact type/case/ordering checks, atomic rollback, storage reload, actual sample/Mock HTTP endpoints and browser edit/reload. They do not constitute original GUI execution or vendor-created directory round-trip validation.

Star-only rules retain a wildcard source marker. Matching skips leading-dot names and slash-containing names, following the inspected original minimatch defaults. Backslash-containing names fail explicitly because platform normalization has not been established. Patterns cannot start with dot or contain repeated stars, path separators or leading negation. Non-nested comma-separated brace alternatives are bounded to 32 expanded options; empty branches, single-item braces and ranges are rejected. Every expanded branch must satisfy the same bounded wildcard grammar and field-name boundary. Existing Local API rules keep their own broader glob behavior unchanged. The editor labels imported exact/star modes separately and only offers integer/number types.

For imported wildcard rules only, question marks consume one UTF-16 code unit, matching the inspected source minimatch question-pattern length checks: one question mark matches a BMP character but not an emoji surrogate pair, while two can match that pair. Local API rules retain their existing code-point matching. The input-length and matching-computation budgets remain unchanged.

ASCII classes accept literal letter/digit/underscore sets, or one same-category ascending range (a-z, A-Z, 0-9), optionally negated with !. POSIX/Unicode classes, mixed-category ranges, escaping, literal dot, caret negation and ambiguous syntax remain rejected. Source AST inspection shows these ASCII classes do not activate the Unicode regex flag, so imported matching retains UTF-16 units. All class variants share the original dot/path boundaries and existing token budget.

Native number rules also accept @float(min,max,dmin,dmax) with four explicit decimal integer arguments, integer-part bounds within ±1e6, and 0–6 fractional digits. Following the inspected Mockjs implementation, the integer part is chosen within min/max, then fractional digits are appended, with a nonzero last digit. Thus @float(3,3,2,2) produces a number strictly between 3 and 4, and a negative integer part retains its sign. This is intentionally separate from Local API float rules, whose existing interval semantics are unchanged. Omitted arguments, fractional integer-part bounds, higher precision and integer-typed float rules are rejected. Seeded illustrative sampling does not claim the vendor random distribution or random sequence.
