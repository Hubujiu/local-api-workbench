# Bounded duration-mode load execution

Offline2 2.0.0 static package evidence has count and duration modes: work.asar chunk 3160.37032bca12b0.js renders round/time selectors; 5934.7307816c0e10.js passes count or duration to pressure_data. This is static evidence, not an executed original-GUI comparison or proof of all nonpaid capacity limits.

The workbench adds explicit mode `count` (unchanged default) or `duration`. Duration requires an integer `durationSeconds` from 1 through 60. Both modes retain the existing maximum 100 primary iterations and concurrency 10. The request-count field is a hard iteration cap in duration mode, so a fast endpoint can finish before the chosen duration. The UI states that limitation and reports the stopping reason. This is not unrestricted stress testing or full original load-settings parity.

A single deadline abort signal covers primary HTTP, scripts and child HTTP through the existing real execution pipeline. A manual cancel and elapsed duration are distinct; the first observed stop cause wins. At deadline no further iterations start, and active work is interrupted. Existing script budgets, CSV limits, variable/cookie isolation and network permissions remain unchanged. Timers and abort listeners are removed when the run settles. Deadline signaling is not a guarantee of exact millisecond response latency: existing cleanup still completes before returning.

Results expose `mode`, optional `durationSeconds`, and `stopReason` (`count`, `count-limit`, `duration`, `cancelled`). Started interrupted records remain visible with `interrupted`, original errors and assertion evidence; they do not count as passed. The UI calls the count “recorded” and nonpassing records “not passed, including interrupted,” rather than claiming cancelled work completed successfully. P50/P95 still use actual primary-response timing samples only. In duration mode iterationCount remains the configured maximum, not a prediction of completed iterations.

Fixed acceptance uses only owned loopback fixtures: deadline interruption of primary and child HTTP, manual/pre-existing cancellation, cap-first completion, failed assertions and CSV evidence, invalid duration rejection before traffic, legacy default count mode, and the authenticated API route. Browser CI verifies invalid input, navigation persistence, real script/CSV execution and visible count-limit reason. No external-service load tests or original GUI execution are performed.
