# Project-bound interactive protocol sessions

The new project protocol-sessions API binds TCP/WebSocket/SSE connections to the owning project. Start accepts a saved project-local definition or explicit bounded configuration; send/get/stop verify ownership. Project-bound IDs cannot be accessed through another project or the legacy global diagnostic API. The existing global API remains available for existing clients, but cannot claim project ownership by injecting a projectId.

Definitions and runtime credentials follow the one-shot preparation contract. Saved TCP receive encoding is honored. A default message in a saved definition is not sent at connection creation: an explicit send action is still required. No frontend controls were added; this is a backend interface and does not silently migrate the current global diagnostic UI.

## Termination and evidence

The first terminal transition automatically finalizes one immutable session snapshot in the existing project protocol history, including remote completion/error, manual stop, deadline, expiry and graceful application shutdown. Ownership and the saved definition are bound before transport construction, including synchronous connection failures. GET only observes the current persistence receipt and never initiates a save. Repeated or concurrent stops share the same storage promise and record ID. A failed write permits a storage-only retry; if the prior write actually committed but acknowledgement was lost, the retry matches the stored definition/result hashes and confirms it without duplicating the record. A mismatched existing ID fails instead of overwriting evidence. None of these paths reconnects or resends a message.

This is not crash-durable capture of an unfinished session. Restoring a project restores evidence only, never a live connection. Automatic persistence makes one attempt; a failed attempt retains its truthful receipt and permits only explicit stop to retry storage. Pending/failed owned evidence cannot be evicted: it occupies one of the existing fifty slots, and new sessions are rejected when no slot is safely reclaimable. This bounds memory rather than silently losing failed receipts or introducing automatic retries. Graceful server-close callbacks retain Node semantics and wait for in-flight persistence attempts, not a claim that every save succeeded. Only callers explicitly awaiting the new backend `app.close()` interface can observe its drain outcome. Existing desktop `before-quit` calls do not await this interface, and the server entrypoint has no SIGINT/SIGTERM drain handler; desktop quit, signal termination and forced exit are not claimed durable by this change. The idempotent `app.close()` interface returns `{allRecordsSaved, protocolSessions}` with existing per-session persistence receipts plus project/session IDs, so shutdown callers can observe unsaved outcomes. Once shutdown starts, no new explicit storage retry may start; already pending saves drain. Failed in-memory receipts are not recovered after process exit. Process crashes and forced termination are not covered. Existing lifecycle limits remain: five live connections, fifty retained session states, fifteen-minute live lifetime, one-hour expiry, two hundred event previews and eight MiB cumulative accepted display-data bytes. The three MiB persisted-record cap also remains; an oversized final record is reported unsaved, not silently called durable.

Snapshots are independent copies. Finished snapshots do not receive late send/message mutations. Failure state is not changed to success by a later stop. Records distinguish a complete remote close, a manual/deadline capture boundary, errors and dropped/truncated previews. Counts describe retained/dropped events; dataBytes/dataHash describe the event's encoded display representation, not a claim that UTF-8 preview text reconstructs arbitrary TCP bytes. Choose hex/base64 receive encoding for binary preservation.

Every preview carries its full representation byte count and hash. A truncated preview is flagged and never splits a surrogate pair. Dropped events and overflow are explicit; manual/deadline closure or any truncation is partial, and an error is failed. Local send progress remains queued/written/failed, not remote business acceptance. Credential configurations are absent from stored definitions/results; application payloads can still be sensitive.

Records participate in project reload, inert backup/restore and existing read-only MCP history tools. Tests cover real multi-send TCP, project/global access denial, duplicate finalization, SSE remote completion, WebSocket event-window truncation, credential omission, both pre-write and post-write-acknowledgement storage failures, error-state preservation, preview integrity and immutable snapshots. Exact-head cross-platform CI remains required.

## Normal host exit (PR40 continuation)

The Node entrypoint (`src/server.mjs`, not a separate `src/main`) joins SIGINT/SIGTERM to one service `close()` promise, including signals received while service startup is pending. Repeated signals join that attempt: they do not retry storage, reconnect, resend or implicitly force termination. Confirmed protocol-session persistence exits successfully; unconfirmed persistence or a close exception sets exit status **2**, consistent with the CLI infrastructure/persistence failure convention. Existing nonzero host status is not overwritten by success. Fixed, synchronous stderr diagnostics exclude raw causes, credentials and paths. A logging failure itself cannot produce a successful outcome.

The desktop main process registers its close hook as soon as the service is ready, before creating/loading the window. It waits at Electron `will-quit`, **after** window close/unload was accepted; cancelling the existing unsaved-edit dialog does not stop the backend. Once approved, repeated events join one drain, then the host exits 0 or 2 without recursively calling `quit`. This changes no renderer, dialog or visual design. Event order follows https://www.electronjs.org/docs/latest/api/app#event-will-quit .

Normal HTTP work retains Node's existing graceful finish/timeout behavior. There is no new forced-connection cancellation, shutdown deadline or retry policy. `app.close()` acknowledges project TCP/WS/SSE history only; this is not a new promise that all background import work is durable. Strong termination, crashes, power loss, OS session shutdown, and desktop exits before a service exists are not covered. POSIX child-process signal tests are explicitly unavailable on Windows because `child.kill()` there does not deliver these catchable signals; portable handler tests and actual packaged Electron quit tests cover different contracts, not a substitute claim of Windows POSIX behavior.

`host-shutdown-process.test.mjs` uses the real Node main, loopback TCP/WS/SSE, new Store reads, process restart, genuine filesystem corruption and in-flight owner HTTP. `desktop-shutdown-smoke.mjs` is a separate packaged Electron CI check for renderer cancellation, successful three-protocol shutdown/restart and failed persistence exit; it does not run script probes. Local environments without Electron/Xvfb cannot claim that GUI-host test passed. No new dependency or runtime budget is introduced.
